# 基础存档系统

2026-11-20；负责人会话 `01a1d420-943b-7db0-adfe-813c342484cb`。

## 当前交付边界

已实现独立的基础存档服务、类型化模块分区、版本迁移、双槽恢复、桌面文件后端和微信原生存储桥。
**尚未接到 Main，也没有开始保存动物、地图、护理、游戏时间或战斗进度。** 当前 Main 重启仍创建新业务状态，不能把基础库测试通过理解为正式游戏已经支持续玩。

后续接入不需要修改底层文件格式：模块定义自己的纯数据 DTO、固定分区 ID 和版本号，在装配入口注册；业务检查点统一提交相关分区，启动时先读齐并校验，再创建完整会话。不要只恢复时钟却重置动物/地图，也不要直接序列化 MonoBehaviour、Prefab 或整个 GameLoopSession。

## 选型与职责

| 项 | 决定及原因 |
| --- | --- |
| 当前问题 | 正式流程仅有内存状态，缺少跨进程保存、升级兼容和坏档保护 |
| 简单替代 | PlayerPrefs 或单文件直接覆盖无法满足异常区分、跨模块检查点和恢复证据要求 |
| 选择 | `Framework/Persistence` 普通 C# 服务，无 Unity/业务依赖；`ISaveStorage` 隔离渠道 |
| JSON | 使用工程已经实际解析的 Unity Newtonsoft JSON **3.2.1**，提升为 manifest 直接依赖，未升级版本；SDK声明的3.0.2不是实际lock版本 |
| 状态所有者 | 游戏装配入口持有一个 SaveService，显式传给所需业务；不是静态单例或全局查找 |
| 事务范围 | 多分区在一个内存副本中捕获、验证，整份写入一个槽；服务成功返回后才承认该检查点已保存 |
| 排除 | 不接云档/账号/加密/支付发货，不定义离线收益、重开战斗或重置规则，不加自动退出存档 |
| 成本 | 每次检查点克隆及序列化整份文档，非逐帧路径；适合当前小体量，增长后以测量决定是否拆档 |
| 撤回 | 没有改正式场景或玩法状态；移除基础库不会改变 Main 现有流程，不应删除任何玩家存储 |

程序集：`HomelessPetHelper.Framework.Persistence`，`autoReferenced=false`。后续接入的程序集须显式引用；使用 JSON 属性/迁移的程序集还须在 `overrideReferences` 中列出 `Newtonsoft.Json.dll`，参照基础库/测试 asmdef，不修改第三方包。

## 最小接入示例

下面是示例，不代表已经确定要保存的正式设置字段。每个 DTO 放模块自己的文件，并保留构造器/字段供 IL2CPP 使用；新增列表/字典等泛型结构还须按 Unity Newtonsoft 的 AOT 要求补保留与目标构建验证。

```csharp
using Newtonsoft.Json;
using UnityEngine.Scripting;

[Preserve, JsonObject(MemberSerialization.OptIn)]
public sealed class SettingsSaveData
{
    [Preserve, JsonProperty("musicEnabled", Required = Required.Always)]
    public bool MusicEnabled;

    [Preserve]
    public SettingsSaveData() { }
}
```

装配入口创建和注册分区，保存期间持续使用**同一个分区定义实例**：

```csharp
using System.IO;
using HomelessPetHelper.Framework.Persistence;
using UnityEngine;

var settings = new SaveSection<SettingsSaveData>(
    "settings", 1,
    () => new SettingsSaveData { MusicEnabled = true },
    data => null); // null 表示验证成功；实际进度/数值必须写合法性校验。

var saves = new SaveService(new FileSaveStorage(
    Path.Combine(Application.persistentDataPath, "player-save")));
saves.Register(settings);

if (!saves.TryOpen(out var status, out var openError))
{
    // 由装配入口进入恢复/错误状态，不创建默认档并自动覆盖。
    throw openError;
}
if (!saves.TryRead(settings, out var restored, out var readError))
    throw readError;

// 用已验证的 restored 创建/恢复模块，随后在明确的业务检查点提交。
if (!saves.TryCommit(writer => writer.Set(settings,
    new SettingsSaveData { MusicEnabled = false }), out var saveError))
{
    // 失败不代表落盘一定未发生。按错误类型报告并按下节处理。
    throw saveError;
}
```

`TryOpen`/`TryRead` 不写盘。缺少某个已注册分区时，`TryRead` 返回工厂产生并验证后的独立默认副本；不会自动把它加入存档。返回 DTO 和传给 `Set` 的 DTO 都不与已提交文档共享可变状态。

多个相互关联的数据同一次提交，例如 `writer.Set(station, stationSnapshot)`、`writer.Set(world, worldSnapshot)`、`writer.Set(map, mapSnapshot)` 放同一 `TryCommit` 回调。任一捕获/验证失败，均不落盘，也不提交其中一部分。捕获、校验和迁移回调应是无副作用的纯数据操作，不在里面修改业务状态、发奖或调用服务。

**持久化事务不自动回滚游戏内存。** 资产/进度接入时，业务服务还要定义检查点失败后的保留、阻断和重试；不能仅因存档底座支持多分区就宣称发奖幂等已实现。

## 文件与异常恢复

桌面后端使用调用者指定目录内的 `save-0.json`、`save-1.json`。每次只覆盖较旧/非活动槽，最新验证通过的槽在整个写入中保留；通过文件 `Flush(true)` 和完全一致的读回校验后才更新内存版本。不是先删除唯一好档的单文件方案。

每个槽是独立完整检查点：JSON payload、SHA-256、格式版本、递增 revision、各分区版本和数据。SHA-256用于发现意外损坏，**不是防作弊或服务器权威**。

| 结果 | 行为 |
| --- | --- |
| `New` | 两槽确实不存在；允许读取模块默认数据；不立即写盘 |
| `Loaded` | 选择最高有效 revision；同版本但不同内容视为冲突 |
| `Recovered` | 一个槽结构/校验损坏，读取另一槽；`RecoveryWarnings` 保留槽号和异常链；打开时不修改文件 |
| 两槽均损坏 | `Corrupt`，禁止读取默认档和保存；原文件不改，待恢复/用户确认流程 |
| 读取错误 | `StorageReadFailed`，不伪装成新玩家；原数据不改 |
| 已知分区校验/迁移失败 | 阻断打开，保留原档；不自动以更旧业务快照回退，避免丢进度或将不兼容当损坏 |
| 更高格式/已知分区版本 | `FutureVersion`，即使它在较旧槽也阻止降级覆盖 |
| 写入/读回/归档失败 | `WriteUncertain`，禁用后续保存，先重新 `TryOpen` 判定实际有效检查点 |
| 外部改变槽内容 | `Conflict`，禁用保存，重新打开，不用旧会话覆盖新数据 |

恢复后第一次需要复用坏槽时，后端先复制坏槽到 `.damaged-<随机ID>` 并验证，成功才覆盖原槽；归档失败不会继续覆盖。归档不会自动清理，后续恢复工具需在人工确认或明确保留策略下管理，避免长期占用渠道配额。没有自动清档/重置/删档入口。

仅支持单线程、单拥有者。保存前内容检查能拦截已经发生的外部改动，不是跨进程锁，不能支持两个真正并发写者；多账号/多窗口需由未来装配层隔离存储路径/前缀。

## 版本升级

稳定分区 ID 发布后不要改名；字段改名、删字段、含义/单位/枚举变化须提升分区版本，增加逐级迁移。例如：

```csharp
var migrations = new Dictionary<int, Func<JObject, JObject>>
{
    [1] = data =>
    {
        data["musicEnabled"] = data["musicOn"];
        data.Remove("musicOn");
        return data;
    }
};
var settings = new SaveSection<SettingsSaveData>("settings", 2,
    () => new SettingsSaveData { MusicEnabled = true }, data => null, migrations);
```

迁移只在副本进行，所有步骤成功并通过模块验证后才用于读取；打开时仍不写盘，下一次显式检查点提交才持久化。重开会从原档重新迁移，不在原对象累加；缺步骤、抛异常或校验失败均保留原档并阻断。

未安装/未注册的分区及未知的文档/分区元数据原样保留。已注册 DTO 的未知字段严格拒绝，而不是反序列化时忽略后悄悄丢失；示例字段用 `Required.Always`，避免缺字段被语言默认值掩盖。重复JSON键、非法版本、同revision冲突、额外JSON尾部都拒绝。不允许远端指定类型（`TypeNameHandling.None`）。

## 微信适配

微信构建在 SDK 初始化及运行环境准备好后，显式注入 `new WeChatSaveStorage("homeless-pet.local.v1")`；命名空间为 `HomelessPetHelper.Framework.Persistence.WeChat`。该前缀是存储命名空间，不应每次发版更换，否则会看起来像新玩家。普通 WebGL/Editor 不可使用该后端，`FileSaveStorage` 在 WebGL Player 也会明确拒绝。

微信桥使用 `wx.getStorageInfoSync` 判断真正缺键，再通过 `getStorageSync`/`setStorageSync` 读写。没有使用SDK中“异常也返回defaultValue”的便捷getter，也没有以PlayerPrefs或Editor内存替代渠道存储。桥接异常、错误类型、缺少wx运行环境都返回失败；完整内容由C#服务读回核对。

适配器对每槽JSON限制 **900 KiB UTF-8**，这是保守内部预算，不是平台最大额度保证。双槽与坏档归档共同占用本地存储配额，超配额按失败处理；当前没有压缩、分片、云恢复。新增分区要评估整个封装后JSON的大小而非仅DTO原始大小。

微信隐藏/切后台时的检查点触发要由正式装配层与已有生命周期统一接入并去重；关键业务操作先及时保存，不能只依赖退出回调。不要每帧保存，也不要在每个组件各写一份独立档。

**微信转换、IL2CPP/AOT实际DTO、真机存储/强杀恢复、容量和耗时仍未验收。** Node桥接测试只验证真实jslib在可控wx桩下的行为，不替代微信客户端或SDK转换测试。
