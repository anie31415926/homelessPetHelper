# Main 双救助与站内续玩实现方案

2026-11-20，依据用户认可的推进建议及“写方案后开工”授权。[任务与验证状态](协作任务/20261120-Main双救助与续玩-01a1f74d.md)独立维护。

## 本轮目标

正常打开 Main，即可从地图完成一猫一狗两次真实逆塔防救助，带回两只独立个体；检查、部分清洁/梳理后仍能看到同一个体，关闭再打开时恢复站内成果。复用现有场景、猫狗攻防、站内场景、护理和双槽存档，不创建另一套原型。

## 实施顺序与范围

1. **正式相遇配置化**：在 Game 配置中显式定义请求模板→动物定义→猫狗攻防内容的对应，以及初始健康样本、护理许可、脏污/浮毛。Main 不再在代码中限定 parking/cat.shy；胜利仍须真实 Won，失败/退出不入站，回站沿用容量和必要检查门槛。
2. **两次救助**：沿用当前容量 2，预置两条可入站普通求助，分别在既有地点出现；让第二次外出有明确可选内容。两条求助均为手工制作内容，不做无限刷新或随机生成动物，不把原“主人直接接回”的事件改成入站事件，另设普通狗求助模板。
3. **站内同个体承接**：沿用已有检查和自愿洗梳。恢复必须保留当前状态与入站历史的区别，不能重新抽动物、把未知伤病判健康或把清洁当治疗。猫狗使用已有图和护理遮罩；本轮不新增美术或动画，不做医疗、关系成长、脏污自然增长或领养。
4. **稳定站内检查点**：用既有 SaveService 保存一个版本化 Main 业务分区，原子涵盖动物身份/当前状态/入站事实/检查、请求状态、世界时间及每只动物实际洗梳采样和已结算工作。模块提供显式捕获/恢复边界；Game 只编排及映射 DTO，不反射/序列化 MonoBehaviour 或整个运行对象。
5. **Main 装配**：真实 Main 启动先读齐校验再构造会话；正式存储路径与音频偏好分离。旧 Editor 预览及直接构造的测试默认内存模式，不能写玩家目录。

## 保存与恢复边界

- 首轮只续玩**站内检查点**，不保存进行中的逆塔防、地图界面或表现动画。外出前先保存站内快照；局中退出后回到出发前站内检查点，不声称可以续战。这个边界须在游戏的既有反馈区域说明。
- 回站结算、基础检查、主动结束有效护理后保存；查看、点选、抚摸和待机不重复写盘。暂停/后台不结算护理或推进世界时间；护理进行中强杀只恢复上一次明确保存成果。
- 同一次快照一起保存动物、请求、护理与时间；恢复创建新的运行会话身份，但保留动物/请求/已入站外出 ID 等业务身份。读取不重播胜利、入站或扣时，已完成求助不能再次生成动物。
- 原始 mask、剩余采样、初始总量和结算分钟共同校验。恢复后继续护理不能重新散布污渍、把已擦区域当未做或重复计时。
- 读档失败保留原档，显示明确反馈并阻断正常流程，不以空站自动覆盖。写入失败保留当前内存成果并阻断继续修改，避免误报已保存；检查点错误不自动新建随机存储路径掩盖故障。坏槽恢复沿用底座证据保留。
- 新增内容和存档结构校验非法 ID、枚举/范围、重复动物/请求/外出及跨模块关系；不兼容数据明确拒绝。无离线收益或挂机推进。

## 选型与迁移

实际问题是 Main 固定样本、两次救助无法自然衔接及成果不落盘。采用现有 Game 显式装配与 SaveService 分区，新增少量配置和模块快照，不引入 DI 容器、资源框架、通用事件总线或新存储后端。首次业务分区版本为 1；旧程序此前只写音频，没有 Main 业务档，无需伪造旧业务迁移。后续字段变化按底座逐版本迁移。

本轮 2 容量、健康样本、现有护理时长和两条求助都是可调试做内容，不升级为正式平衡。领养/无限供给、伤病处置、亲密关系及战斗中断恢复仍需独立方案，不能用本轮实现补成默认规则。

## 验证与验收

- EditMode：配置拒绝、猫狗选取、真实结果桥接、同个体入站、请求/时钟/检查点一致性、部分洗梳续做与不重复耗时、两次重建和双槽坏档/写失败/非法快照无覆盖。
- PlayMode：保存 Main 控件驱动猫狗两次救助、检查和自愿护理、两个独立身份/站内选择、退出后重建恢复；沿用原暂停、背景切换和旧预览回归。使用临时存储注入，不碰玩家档。
- 执行基础源码/生成一致性及必要图形测试；保存隔离输入和报告对应关系。图片未变不生图；正式渠道、微信强杀/AOT、触摸性能与最终美术仍按实际条件另验。
- 完成时回写本方案实际结果、协作任务及统一入口，先更新状态再追加 delivery 执行记录。未获要求不提交推送。

## 已落地的代码边界

- `CityMapConfig.json` 增加独立 `ordinary-dog` 求助和 `rescueEncounters`；单车棚进入 cat，小院进入 dog。动物初始健康、饥饿、许可、毛发表面数值、战斗 profile 及洗梳时长在配置中显式提供，经 GameContent 校验；原寻宠直接交接事件保留其语义。
- `MainProgressSession` 拥有 Main 业务会话、`StationCareRoster` 和外出→求助关系；`MainProgressCodec`/`MainResidentCodec` 只映射独立 DTO。业务分区为 `main.station` v1，存储路径为桌面 `main-progress` 或微信 `homeless-pet.main.v1`，与音频偏好分开。
- `RescueStation.RestoreResidents` 原子恢复名单和基础检查；`StationAnimalIntake.Restore` 分开保留入站历史与当前个体。历史容量/顺序按本轮固定容量、无移出规则恢复，不提供容量扩建或领养存档契约。当前 v1 仅支持明确健康的两条制作内容，遇到伤病/不支持的检查快照拒绝读取，不能省略或清空健康资料来兼容。
- `StationCoatCare`/`DirtField`/`CareWorkMeter` 保存原始总量、剩余每格采样、遮罩、初始毛发表面条件、洗梳时长和已结算分钟；恢复后不重新生成采样。全量校验在暂存会话上完成，成功后才发布给 Main；新运行会话 ID 不复用。
- Main 在开地图前、回站结算、完成基础检查和主动结束护理后提交检查点；界面显示外出/护理中退出的恢复边界。坏档不新开空站、不覆盖原槽；保存失败停用后续玩家操作，内存成果仍可供诊断。没有依赖退出回调保存。
- `MainGameRoot.ConfigureProgressStorage` 是 Start 前的显式存储注入，真实 Main 流程测试使用独立存储；直接构造 presenter 和旧预览仍默认内存模式，没有正式包测试旁路。
- 连续同帧关闭/开启战斗暴露了旧 Cell 延迟 Destroy 的问题；`SiegeCellPool.Dispose` 先失活再销毁，专项控件测试保持同帧连续操作验证。恢复后的检查门槛不覆盖旧协调器的暂停/基础设施失败优先级。

## 试玩路径

打开 `Assets/Scenes/Main.unity`：外出救助 → 单车棚 → 正常完成猫战斗并回站 → 进入站内 → 选猫并查看健康，可按需局部洗梳 → 返回站内 → 外出救助 → 小院 → 正常完成狗战斗并回站 → 选狗查看健康。此后重进 Main，会看到原来的两只动物及已结束护理的成果；清洁不要求一次做完，也不是继续救助的门槛。

局中退出会回到出发前的站内记录；护理中退出会丢弃上次主动结束之后尚未提交的工作。暂停/后台不会替玩家结束护理，不推进离线时间。两条普通求助完成后不会无限刷新；原主人交接事件仍未接入真实直接交接结算，不应按入站救助完成处理。
