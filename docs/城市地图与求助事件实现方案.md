# 城市地图与求助事件实现方案（草案 v1）

> 文档状态：设计草案，**不是开工授权**。整理日期 2026-11-17。

> 接口名、类型名、字段均为设计建议。进入任一模块实现前，按[玩法确认与试做](开发方案与执行步骤.md#玩法确认与试做)逐组确认第 4 节的待讨论项；**本方案获批不等于玩法细节获批**。

## 1. 现状一句话

地图只有设计方向，没有任何实现代码。当前可玩的是四个 Editor 白板（选项、停车棚两起点、救助站），正式 `Main.unity` 仍是工程底座。城市地图、求助事件调度、点位到现场的映射均未实现；Web 原型 `src/outing` 的迷宫/网兜是历史实验，不是城市地图，也不是本方案的移植目标。

本方案要解决的问题只有一个：把"救助站 → 城市地图 → 救助现场"这条已确定方向，拆成可以逐块确认、逐块落地、且不返工的模块骨架。不扩大当前最小试做范围。

## 2. 目标与非目标

### 2.1 最小目标（对应开发方案"第一目标"的一段）

```text
救助站（出发前容量检查）
  -> 城市地图（点位选择，看到求助点/可探索点）
  -> 选一点出发 -> 现场开路（解谜或清理，已有 P3 范围）
  -> 回合交涉救助（已有 P2 范围）
  -> 回站 -> 事件结算一次 -> 展示总结（已有 ST/D 节范围）
```

本方案只新增"救助站到现场之间"的地图与事件调度，以及回站时的事件结算；现场内部与站内照护复用既有模块，不重写。

### 2.2 明确不做

- 可自由移动的开放大地图、角色走位、逐层区域中转页（总纲第 5 节 + B 节）。
- 把迷宫/网兜旧原型当正式外出方案（总纲 B 节历史实验）。
- 事件刷新间隔、并行数量、满员后果等未确认规则写死为正式值。
- 完整经营、经济、两种货币、建设/设施、领养快进的完整流程（G/H 节仍待讨论，本方案只在第 7.4 节留衔接位）。
- 存档、账号、微信导出、正式图片与资源框架（见 P1/P5/P6 门禁）。
- 不修改已有 Prefab、不重建已有底座、不在 `Main` 放跳关开关。

### 2.3 与 Web 原型的关系

`src/outing/engine.js` 中的 `createOuting`、迷宫寻路与站位交涉是独立 HTML 验证，规则仅作行为参考。城市地图与求助调度没有对应的 Web 实现，不能从原型反推点位数量、事件频率或入口占比。

## 3. 已确定的设计约束（直接作为实现边界）

| 已确定方向（出处） | 对实现的硬约束 |
| --- | --- |
| 救助站 → 城市地图 → 救助现场（B 节） | 地图是独立的一层入口，阶段上位于"离站"与"开路现场"之间 |
| 区域与小地点在同一张地图呈现，不设区域中转页（B 节） | 数据结构上"区域"只是点位的分组标签，不是可进入的节点层 |
| 地图用于点位选择，不操控角色自由移动（B 节） | 输入模型是"选点命令"，不是方向键/摇杆连续位移 |
| 不移除现场寻找、清理、解谜（B 节） | 选点只决定"去哪"，不替代开路完成条件；路未通不能交涉 |
| 求助为主、主动发现为辅，两者非互斥（B 节） | 事件模型要同时容纳"带求助的点位"和"可探索点位"，不是二选一模式 |
| 求助事件与地图地点结合（B 节） | 事件持有稳定点位引用，点位与事件显示在同一视图 |
| 避免求助堆积 / 快速满员卡循环（B 节） | 事件供给受在站容量与照护负担约束；满员出发前提醒 |
| 途中补给融入清理通道、顺带获得（B 节） | 补给挂在开路结果上，不做独立采集系统，不因掉落额外推进时间 |
| 出发前满员提醒（G 节） | 容量检查在"出发"动作之前，不在救回后拒收 |
| 世界时间由完整行动推进（A 节） | 一次完整外出＝一次耗时行动，按版本提交一次；不按点击/掉落推进 |
| 现场与站内医护同源（C/E 节） | 地图层不复制医护规则，只传动物身份与现场现场条件 |

## 4. 必须先确认的问题组（一次一组，确认后再编码）

按项目流程，下列都不是本方案能替用户决定的。建议从 A 组开始，一次只讨论一组，先用一轮具体例子走通，再决定是否进入下一组。每组给出少量选项、推荐和代码/美术影响，确认结果回写总纲 B 节后再改实现。

### 4.1 A 组（最先）：地图最小呈现 —— 2026-11-17 已确认

用户确认 A 组方案无误。以下为本组落定范围（**已确定**），仅覆盖"玩家在地图上看到什么、能点什么"，不触及 B 组的事件生成/节奏规则：

- **城市与区域设定**：一张抽象城市底图 + 少量固定点位。区域作为点位分组标签，不是可进入的节点层。
- **初始开放范围**：首版点位全部可见可用；"按等级/建设解锁"暂不做成系统，只在点位定义里保留"开放条件"字段供以后使用。
- **点位数量与形态**：先用少量固定点位（一轮具体例子按 3 个），静态绑定即可；超过一屏才上对象池列表，不提前堆框架。
- **求助点与可探索点区分**：用明显视觉差异（求助角标 / 颜色 / 图标）让玩家一眼分辨"这里有求助"；具体视觉表现留给临时图验证。
- **一轮具体例子（本次验证目标）**：地图上 3 个点位，其中 1 个带求助标记。玩家点求助点 -> 出发 -> 现场；另外 2 个无事件点位的点击行为（进入探索 / 提示暂无事 / 不可点）属 B 组"主动发现"规则，本组不擅自定，留待 B 组确认。
- **临时图授权**：用户允许用本地 ComfyUI 先生成一批**临时图**支撑本组验证，明确**不作为最终版**。临时图放 Editor-only 临时目录，不进正式资源流程；正式图片仍按 P5 门禁与资源评估推进。

### 4.2 B 组：事件调度与节奏

- 事件从哪来、何时出现：开局给一批、按游戏时间逐步出现、还是完成一次外出后出现一个？三种方案对"堆积"和"空窗"影响相反。
- 同时可接事件数量：与在站剩余容量如何对应（1:1 / 预留空间 / 不完全挂钩）？这是 B 节"事件供给匹配空余容量"的落点。
- 求助暂缓、超时、已接未去的事件如何处理：暂缓后再出现还是消失？已接事件能否取消？**这些"后果"已被文档标注为不只是数值问题，必须先确认，不能先写默认行为。**
- 满员时的具体限制：禁止出发 / 允许出发但提示可能拒收 / 强制先送养？G 节只确定了"出发前提醒"，限制方式未定。
- 主动发现入口：无求助时点空点位进入什么？是否消耗一次外出时间？

### 4.3 C 组：点位到现场的映射

- 一个点位绑定固定现场模板，还是可随机切换解谜/清理分支（P3 两种模板）？
- "同一地点的后续事件"：同一点位再次出现求助时，是否复用同一现场、是否复用同一动物？
- 现场到交涉、回站的过渡表现：走路小动画还是直接切场景？直接切换最省资源，动画属于 P5 表现层。

### 4.4 D 组：主动发现与求助表现

- 来电/留言的具体形式（B 节待讨论）：站内弹一条消息，还是地图点位上直接显示？
- 主动发现的触发方式与两类入口占比。

## 5. 分层与模块归属（设计建议）

新增一个独立程序集承载"离站到现场"这段规则，不塞进现有模块，也不反向依赖表现层。命名与现有 `HomelessPetHelper.Modules.*` 一致。

```text
Bootstrap / 装配层（持有会话、显式传依赖、决定阶段与时序）
        |  调用（有向，向下）
        v
Modules.Outing  ──设计建议──>  求助事件调度 + 城市点位规则 + 外出会话
        |                          （纯 C#，可在 EditMode 直接构造测试）
        |  选点后把"现场身份"交给下游；回站时把结果交回装配层
        v
Rescue(RescueFlow/Options)   Station(入站/容量)   WorldTime(时钟)   ← 已有模块，不重写
        ^  装配层把三者按第 8 节契约串起来；Outing 不直接引用它们的可变字段

Editor/OutingPreview（Editor-only）── 仅验证场景、样例装配、菜单入口
Modules.Outing.UI ── 展示与输入，读快照、提交意图，不写规则字段
```

依赖方向必须是 `装配层 → Outing / 已有模块`，`Outing` 不引用 `UI`、`Editor`、`Bootstrap` 或平台 SDK。若事件调度与地图规则各自复杂度上升，可再拆两个 asmdef；首版放在同一 asmdef 内用目录分层即可，不提前拆。

### 5.1 职责边界

| 部分 | 持有 / 负责 | 不应负责 |
| --- | --- | --- |
| 装配层（Bootstrap 扩展） | 创建外出会话、决定阶段、按契约调用各模块、提交一次时间 | 不实现事件生成算法、不替 UI 存第二份状态 |
| 求助调度 | 事件池、事件生命周期、与容量/照护负担的匹配输入、可复现随机 | 不认证书实救助成功、不发奖、不写存档、不决定满员后果 |
| 城市点位 | 只读点位定义、开放条件、点位→现场模板映射、选点合法性 | 不进入现场、不控制角色移动、不复制开路规则 |
| 外出会话 | 本轮身份、seed、所选点位、关联事件、阶段、防重、版本 | 不复制现场/交涉内部规则、不缓存 UI 快照 |
| 表现与输入 | 读快照、提交"选点/出发/暂缓"等意图、反馈 | 直接写规则字段、用动画结束当业务成功凭证 |

沿用[开发方案第 3 节](开发方案与执行步骤.md#3-模块边界与状态归属)的"一轮会话唯一状态归属"原则：地图选点结果、事件状态、外出会话三者由装配层统一编排，不允许多个组件各存一份阶段。

## 6. 数据结构（设计建议，待评审）

遵守"静态定义 / 单局可变态 / 快照 DTO 分离"，只读配置不得被当作运行态修改。字段不写正式数值；数量、时间、随机均由边界传入。

### 6.1 静态只读定义

- `CityMapDefinition`：底图标识、区域分组标签、点位只读集合。区域只是 `RegionId` 标签，不是层级节点。
- `MapPointDefinition`：稳定 `PointId`、显示名 Key、所属区域、开放条件（默认开放 / 由外部解锁标记决定）、可绑定的现场模板标识集合（解谜 / 清理）。
- `HelpRequestTemplate`：事件模板标识、文案 Key、可出现的点位约束、默认关联动物定义标识。**不含**具体动物实例状态。

配置来源：配置生成器尚未选型（Luban 仍是候选），首版用普通只读对象或 Editor 串口装配即可，不引入表生成器；正式配置化留到选型确认后。

### 6.2 单局可变态

- `OutingSession`：会话 Id、seed、所选 `PointId`、关联 `RequestId`、阶段枚举、时间版本快照、是否已结算。**只在构造时固定起点**；普通操作不重置。参照 `CaseAnimal` 的连续状态做法。
- `RequestPoolState`：当前可用 / 已接 / 已暂缓 / 已过期 / 已结算的事件集合，事件实例持有稳定 `RequestId` 与点位引用。
- `PointUnlockState`：已开放点位标记集合；扩展解锁由外部传入，地图模块只读取。

### 6.3 事件状态机（枚举 + 显式方法，不建通用 FSM）

```text
Available --Accept--> Accepted --Resolve--> Resolved(唯一终态)
Available --Defer----> Deferred --Reactivate?--> Available   （"暂缓后是否回来"待 B 组确认）
Available --Expire---> Expired                              （"是否超时"待 B 组确认）
Accepted  --Cancel---> Available 或 Deferred               （"能否取消已接"待 B 组确认）
```

单一迁移入口（建议 `RequestPoolState.TryTransition` 语义），迁移成功才改状态；非法/重复迁移返回明确失败且不留下部分修改。未确认的迁移分支先不实现、不加隐式默认，等 B 组确认再补。

### 6.4 快照 DTO（只读，供 UI）

- `MapViewSnapshot`：点位列表 + 每点显示状态（可接求助 / 可探索 / 暂未开放）+ 可用事件摘要。
- `OutingSummary`：本次外出结果（成功 / 求援 / 暂缓 / 失败）、所选点位、用时摘要、动物身份与当前状态引用。不含照护操作，符合 D 节"总结面板只展示信息"。

快照不可变：旧快照不随后续状态变化而改变，与 `CaseAnimalSnapshot` 一致。

### 6.5 随机与时间边界

- 随机：以 `seed + 事件模板版本` 为输入，同种子可复现；不承诺跨语言序列一致，配对测试固定初始状态与操作序列。
- 时间：只接受装配层传入的整数游戏分钟与进入时保存的版本；不在地图层读现实时间、不挂机补算。
- 数值：并行事件数、刷新间隔、容量上限、暂缓/过期行为均为**待确认参数**，由调用方传入，不写死在结构里。

## 7. 关键流程（建议骨架，分支规则待确认）

### 7.1 一次正常外出（成功路径）

1. 玩家在救助站点"出发"：装配层先做出发前容量检查（G 节已确定的提醒），满员则给提示并按 B 组确认的限制处理。
2. 装配层创建 `OutingSession`（固定 seed、会话 Id、时间版本），请求 `MapViewSnapshot` 并打开地图视图。
3. 玩家选点：提交 `PointId`。调度层校验点位开放 + 事件处于 `Available`；成功则事件转 `Accepted`，会话绑定点位与事件，打开现场（进入既有开路阶段）。
4. 现场开路、交涉、收尾由 P3/P2 既有模块完成；地图层不介入。（现场模板由点位映射给出，C 组确认。）
5. 救助成功：装配层按[模块交接契约](开发方案与执行步骤.md#模块交接契约)核对会话与身份，调用 `RescueStation.TryReceive` 一次，事件转 `Resolved` 一次。
6. 回站总结：`OutingSummary` 只读展示；装配层在完整外出开始时保存的时间版本上，提交一次 `ActionWorldClock.TryAdvance`。
7. 会话结束并清理；重复"回站/结算"调用被防重拒绝，不新增动物、不重复推进时间。

### 7.2 事件调度与容量匹配

调度层在生成/激活求助时接收"当前在站数、剩余临时容量、照护负担输入"（由装配层从 Station 读取），据此决定是否激活新事件。这是 B 节"事件供给匹配空余容量"的技术落点；具体匹配公式属 B 组待确认参数，不在此定死。

### 7.3 暂缓 / 失败 / 求援 / 满员分支

- 求援：沿用案例"只结束本次试做，不算成功、不入站、不发奖"的方向；在正式规则确认前，地图层只提供"结束外出且事件不结算为成功"的通道，不冒充失败或死亡。
- 失败、暂缓、过期、满员拒出发的具体后果**未确认**（B 组），本阶段只保留状态位与提示位，不写默认惩罚、不自动删除动物、不强制送养。
- 所有失败/拒绝按 `TryXxx` 契约：返回明确原因，不留下部分修改，不推进回合或时间。

### 7.4 世界时间与容量衔接（留位，不实现完整流程）

- 一次完整外出＝一次耗时行动（A 节已确定），选点、掉落、拾取、查看地图都不额外推进时间。
- 主动快进到领养机会属 G 节已确定方向，但完整流程依赖领养事件与健康结算（尚未实现）。本方案只在会话层预留"快进是一次显式行动、也要按版本提交一次时间"的约束，不把大额 `TryAdvance` 当快进实现。

### 7.5 暂停 / 失焦 / 重入

- 参考现有会话契约：暂停、失焦、切后台冻结玩法时间与输入，回前台不补算。
- 旧会话 Id / 旧时间版本的回调不得作用于新会话；显式重开才创建新会话。

## 8. 与现有模块的衔接契约（设计建议）

| 衔接点 | 做法 | 不改动的边界 |
| --- | --- | --- |
| `RescueFlow` 阶段 | 建议新增一个地图阶段，位于 `Station --LeaveStation--> Map --Depart--> Approach`；仍由单一 `TryAdvance` 入口控制，地图选点成功作为信号来源 | 不改"完成信号来自规则校验、不是 UI 跳关"的原则；`RescueFlow` 目前只持有阶段顺序，不让它管事件算法 |
| `RescueStation.TryReceive` | 回站接收同一动物身份，重复调用拒收；入站数据仍只承接上游事实 | 不绕过身份校验、不在地图层生成动物 |

### 14.2 M2 会话串联（2026-11-18 落地）

- **改动范围**：改 `Modules/Rescue` 的 `RescueStage` / `RescueSignal` / `RescueFlow`（插入 Map 阶段）；改 `Bootstrap` asmdef（新增 Outing/Station/WorldTime 引用）；测试 asmdef 加 Bootstrap 引用；未改任何 Prefab、`Main.unity` 或 UI。新增 `Bootstrap/OutingCoordinator.cs` + `OutingAssemblyFailure.cs` 与 1 个 EditMode 测试类。
- **RescueFlow 阶段**：`Station -(LeaveStation)-> Map -(Depart)-> Approach -(ApproachCompleted)-> Negotiation -(NegotiationCompleted)-> Rescued -(ReturnToStation)-> Care -(CareCompleted)-> Station`。阶段/信号枚举值顺延插入 Map/Depart=1，保留"阶段 i 的合法离开信号是信号 i"的对应关系；`RescueFlowTests` 循环边界 5→6、CompleteLoop 加 Depart、越界值与 Suspension 用例同步。
- **装配协调器**：纯 C#（无 Unity 依赖），构造注入 Flow/Station/Clock/MapRules/RequestPool + 三个会话 Id，持有唯一活跃 `OutingSession`。四方法：
  - `TryBeginOuting`：无活跃会话 + seed + Station 阶段 + 站点未满 + 未挂起校验 → 建会话、捕获游戏时间版本、`LeaveStation`。满员只返回拒绝，不写默认后果。
  - `TrySelectAndDepart`：`CityMapRules.TrySelectPoint` 只读校验 → `Accept` → `session.TryDepart` → `Depart`。无事件点位只报事实（B 组）。
  - `TryAdvanceField`：只注入已验证的现场信号（`ApproachCompleted` / `NegotiationCompleted`），校验会话身份与阶段匹配后转发；协调器不自造成功信号，两条开路分支在此汇合。
  - `TryReturnAndSettle`：全量前置校验（会话身份/阶段/到达身份=会话Id/duration/站点容量/时间版本）→ `session.TrySettle` 闸门 → `Resolve` → `station.TryReceive` → `clock.TryAdvance`（用出发时保存的版本，一次）→ `ReturnToStation` + `CareCompleted` → 产出只读 `OutingSummary`。
- **红线遵守**：跨模块提交靠"校验段只读、提交段前置已保证"避免中途失败；重复结算在会话闸门被拒，不新增动物、不重复推进时间；现场成功不由地图层伪造；暂缓/过期/取消/满员后果仍不写默认行为。
- **未实现（按约束留位）**：现场开路/交涉运行时规则（当前只有 Editor 案例与 Options 骨架，靠注入已验证信号跨越）；事件生成与容量匹配算法（B 组）；点位→现场模板映射的运行时使用（C 组）；UI / Editor 白板（M3）。
- **验证**：`node tools/check-unity.mjs` → 0 issues（101 脚本、12 程序集）；EditMode 先 `EditMode-isolated-MapStage.xml` 验证阶段改动 214/214，再 `EditMode-isolated-M2Coordinator2.xml` → 226/226 通过，其中新增 `OutingCoordinatorTests` 13 例（完整成功路径、重复结算防重、错会话、无求助点位、暂停、跨外出身份、跳阶段、两分支复用、旧会话拒绝等）。
- **剩余风险/待判断**：协调器的提交段非事务（正常路径前置校验已覆盖所有失败点，异常并发需另评估）；三处会话 Id（flow 无 Id、station、world）由构造方保证一致；M3 白板接线时需把底图点位点击接到 `TrySelectAndDepart`，现场试玩结果经校验后调 `TryAdvanceField`。
