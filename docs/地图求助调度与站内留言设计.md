# 地图求助调度与站内留言

2026-11-24。承接[城市地图与求助事件方案](城市地图与求助事件实现方案.md)的事件调度。已确认的目标：正常可出发且有可用床位时，地图至少有一件救助可做；居民留言可以早于腾位，随游戏时间失效；空位越多只略微提高留言频率，腾位不触发即时来电。五位以上是正式版容量方向，当前试玩容量不在这次改动中锁定。

## 事件流程

1. 保留开局线索。站内稳定检查点核对时间、空余床位和活跃求助。需要新事件时，只选已开放、具备真实救助关卡的地点。每地点至多一条待处理或已接普通求助；新事件有独立身份，优先轮到较久未生成的地点。场地清障进度沿用地点存档；原事件中途回站沿用原动物和现场状态。
2. 地图保底只在还有床位、没有待处理普通求助时补一条，不等电话。满员不发保底，既有任务保留。无合格内容时仍按地图原有不可出发反馈，不生成无法完成的任务。
3. 留言使用游戏分钟。在有足够时间间隔、没有仍有效的留言、存在可用地点时，有资格产生一条；和地图共用请求，不自动接单或锁床位。达到旧的到期时点后只在时间实际推进的检查点生成，不补发一串历史留言。新开档从当下安排首个等待期；送养、扩容、查看地图和重启本身不会推进它。
4. 未出发的留言过期，由其他救助者接手，地图不再可接。已确认出发的请求受保护；中途回站后恢复为可接，并重新给短暂处理窗口。过期不算玩家成功、失败或奖励。保底任务独立补足，不被来电到期卡住。

试玩参数（配表调整）：留言有效期 120 游戏分钟；空位 0、1～2、3 以上时最短间隔分别为 240、180、150 游戏分钟；新档首条留言也要等到相应间隔。间隔按已有周期固定，腾位不会缩短正在等待的周期。现有可玩候选为单车棚、居民小院；占满候选时暂缓，后续加地点扩充候选表。正式节奏、机会比例及重复内容以试玩结果调整。

## UI 流程

| 页面/状态 | 玩家看到什么 | 操作 |
| --- | --- | --- |
| 救助站首页（新留言） | 站内仍以动物与场景为主体；空闲且靠近自然流程边界时，出现一张共享手绘纸板「救助消息」，说明地点与线索。 | 有空位时「查看地图」或「稍后」；满员时说明先腾位，仅关闭。查看不接单。 |
| 正在护理、确认、结算或外出 | 不中断手势、不叠弹窗；留言待下一次安全展示，地图仍可查。 | 继续当前操作。 |
| 地图 | 保留全屏与角落返回。普通打开时点地点才展开详情；从留言跳转时定位其地点并展开同一张详情。 | 玩家仍显式确认发起外出。 |
| 留言已被接手 | 仍未看过时可提示「已接走」的短结果；地图地点的旧求助消失。 | 关闭；若有空位可选其他求助。 |

复用共享弹窗、全屏遮罩、字体和动效，按钮沿用安全区内既有热区，不在顶中或地图新增常驻栏。正文短句，拒绝原因可持续阅读；不要求新图、电话铃音、秒级倒计时或系统通知。首版以回站/安全站内时机展示一次，稍后从地图查。

验收走查：满员收线索 → 腾位未产生新提醒 → 仍有效可出发；过期后其他救助者接手 → 有空位仍有别的可玩事件；出发保护 → 中途回站续同一动物；重进不重抽、不补播；连续完成原猫狗后还有任务。按[排版](UI排版与可读性规范.md)与[样式](UI视觉样式规范.md)检查短屏、安全区、弹窗层级和提示文字。寻宠交接、主动探索和更多正式关卡不在本次范围。

## 首版实现与试做记录

- `CityMapConfig.json` 的 `dispatch` 段分别配置时间和地点候选，新增候选须匹配正式事件模板、动物和已装配的现场。首版只有单车棚、居民小院各一套模板；重复出现是不同个体，仍复用相应模板和现场。无合格地点时不制造空关。
- `RequestDispatch` 使用请求池和游戏时钟，在正式 Main 稳定检查点调度。送养提交保留原子性；腾位后首次打开地图前执行保底检查，不为此发送被动留言。未出发留言到期进入已有的「其他人接手」终态。曾出发的留言在中途回站后重新获得有效窗口。
- 存档段 `main.station` 从 v3 升 v4；旧档保留居民、纪念、请求、时钟和现场，新调度从旧档当前时间起算。留言身份、期限、下次时间、出发保护和展示标记随现有事务提交。当前保留终态请求供跨档引用和轮换排序，长期大量事件的历史归档策略另行评估。
- 隔离 Windows Editor：EditMode 专项 33/33，PlayMode 专项 2/2；后者连接站内弹窗、地图详情、出发与读档恢复，也复核送养成功/拒绝和失败回退。共享 UI 抓取 6 种窗口，已看 390×844 实图；新文案逐字核对现有字体。记录详见[协作任务](协作任务/20261124-求助调度与站内留言-01a1f74d.md)。未跑全量、微信或真机；正式来电比例与手感待试玩。
