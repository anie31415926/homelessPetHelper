# 图片缩图：开源参考与当前实测

2026-11-20，负责人 Codex `01a1ed54-d51a-76c1-80e3-a5cf24f9cd87`。用户允许小图缩小，前提是正常使用时不明显变糊。本轮是 GitHub 调研和非破坏性候选对比，不是正式资源替换或微信验收。

## 当前选择

- 实际最大显示长边不超过约128物理像素、没有放大用途的独立小图，优先比较128档；96档放到128时已经明显变软，不作为统一默认。
- 显示约160–192px的内容先比较192档；不因为Unity常见Max Size列表只提供2次幂就强行补成正方形。生成的PNG可为矩形/192档，Importer与最终平台输出另验。
- 当前战场共用橘猫/白狗图保留256原图。128档放到224px时明显模糊，192也略软；不能因为文件名仍叫地图角标就全局改成128。
- 四建筑保留原图，192长边是待实际最高渲染尺寸核对的候选，不采用128统一替换。地图布局和透明画布不裁边，不改热点/Prefab。建筑原图已是调色板PNG，盲目缩为RGBA PNG可能增大源文件。
- 护理近景512图、遮罩、动物蒙皮图集不属于本轮小图。特别是已有蒙皮图集的2px补边依赖不缩放等条件，不直接缩图集破坏防串色保证。
- 保留上一轮结论：动物蒙皮使用现有实测有收益的合图，地图UI暂用散图，不为缩图再次启用大图集。

这是当前用途下的保守选择，不是任意机型/缩放下的永久最优。替换前仍须目标渲染尺寸与完整画面A/B；只缩未引用的图不会让实际包变小。

## 本地对比方式

工具：[image-size-preview.mjs](../tools/image-size-preview.mjs)。

```bash
node tools/image-size-preview.mjs
node --test tests/image-size-preview.test.mjs
```

只读取`Assets/Art/CityMap`现有8张PNG，输出到忽略目录`test-results/image-size-review/`，不修改原图/Importer/台账/Prefab。每张保存源SHA256，执行后再次核对原图；报告包含工具SHA256与Sharp版本。未把对比图导入为运行资源，因此没有新增台账资产。

缩图使用Lanczos3、保持比例、不放大、不裁透明画布。预览统一按96/128/224显示尺寸模拟双线性采样，比较深浅背景；这不是Unity/微信逐像素渲染等价证明。非正方形档位整数取整可能产生不足一像素比例差，比较时统一原图显示画布，避免不同长度导致误差统计无效。

普通PNG候选不做额外调色板量化；另生成明确标注`palette-candidate`的256色候选，属于可能有损的编码比较，不自动接受。RMSE只作差异定位，不设置“通过分数”，不把锐化/AI补细节当原图无损。

已目视检查：

- `small-icons.png`、`small-icons-palette.png`：四动物都显示128px，对比原图/192/128/96；128仍较清楚，96变软；细线会有不同采样感，不能声称像素无损。
- `battlefield-icons.png`：猫狗都显示224px，128明显变糊；因此不覆盖当前共用Sprite。
- `buildings.png`、`buildings-palette.png`：四建筑都显示192长边，192较接近，128/96的轮廓与细节变软；调色板是额外有损候选，需要单独看渐变与透明边缘。

实际用途依据：`SiegeBattlefield.Scale`取战场宽/360、高/360的较小值，动物尺寸为`78 * Scale`，蓄力横向最大1.05倍。在1080物理宽、左右32布局padding的宽度上界下约231px，**只是保守上界，不是该机型实测尺寸**。首批已有540×1170和768×1024截图，长短屏动物大小明显不同；本轮查看`cat-army.png`与`dog-768.png`，不把短屏的小图结论套到所有长屏。未新增Unity屏幕测量或真机试验。

## 源文件与像素量实测

下表KiB=1024 bytes；都是候选源PNG，不是包体。192/128默认列是全彩PNG；调色板列另有潜在量化损失。

| 图片 | 原尺寸 | 原PNG KiB | 192长边 PNG KiB | 128长边 PNG KiB | 128调色板候选 KiB |
| --- | --- | ---: | ---: | ---: | ---: |
| 三花猫 | 256×256 | 54.6 | 39.0 | 19.3 | 6.5 |
| 橘猫 | 256×256 | 57.8 | 43.1 | 20.6 | 7.0 |
| 白狗 | 256×256 | 53.0 | 31.7 | 15.6 | 8.3 |
| 兔子 | 256×256 | 44.9 | 27.0 | 13.4 | 6.2 |
| 单车棚 | 208×190 | 13.6 | 44.0 | 22.8 | 7.3 |
| 门廊 | 250×234 | 17.0 | 39.7 | 20.9 | 7.1 |
| 救助站 | 294×218 | 16.3 | 31.2 | 16.7 | 5.7 |
| 小院 | 354×211 | 24.9 | 30.4 | 15.8 | 6.0 |

四动物若全部仅作小图，从256到128：源PNG合计215273→70555 bytes（210.2→68.9KiB，约少67.2%）；RGBA32基础像素合计1MiB→0.25MiB（少75%）。192档源PNG140.7KiB、RGBA32为0.5625MiB（少43.75%）。这是条件化对比，不是已省下实际包体；猫狗当前复用不实施该统一降档。

四建筑原PNG共73615 bytes（71.9KiB）；192普通PNG反而148821 bytes，192调色板候选47514 bytes（46.4KiB，约少35.5%），其RGBA32基础像素947224→469248 bytes（约少50.5%）。原因是原图已为调色板PNG，缩放会产生新颜色；只看像素数会错判文件收益。量化源PNG的节省不会让同尺寸RGBA32的GPU纹理自动变小。

**对20MB担忧的结论**：小图规格值得早定，但不能仅靠PNG数字承诺总包够用。先按最大实际显示像素选档，再测Unity导入/压缩及微信转换产物；引擎代码、字体、音频、贴图和首启必需请求分别预算。保留既有2MiB首启图片内部目标，不把它当渠道总配额或已达标。官方不同文档/已安装SDK对总额度有20/30MB的历史差异，真实AppID及当前开发者工具仍未核验，继续按用户20MB保守规划，不擅自放宽。
