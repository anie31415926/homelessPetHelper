## 12. Perforce (P4) 版本管理

> 面向小团队、高频迭代的竖屏休闲项目。本节不假设任何具体 depot / stream 命名与本机工作流；命名按 [§15.4](../reference.md#s-15-4) 替换。若项目改用 Git，见 [§12.6](#s-12-6) 映射。

<a id="s-12-1"></a>

## 12.1 流与分支策略

- **推荐**轻量结构：主干（日常迭代）+ 发版分支（提审/灰度）+ 紧急修复分支；每次提审包打标签（Label），便于回溯与回滚。
- **禁止**长期存在的个人分支；**必须**至少每日同步一次主干，避免大合并。
- **必须**发版分支只收缺陷修复，新功能只进主干；禁止在发版分支直接改配置 schema 或面板生成逻辑。

<a id="s-12-2"></a>

## 12.2 Changelist 规范

```
[模块][类型] 一句话描述（≤ 50 字）

问题/需求：<原因或需求单号>
方案：<关键实现与取舍>
验证：<格式与分析器 / 编译 / 自动化测试 / 按风险补充生成链、面板、真机证据；不适用项说明原因>
影响：<受影响模块、是否需重新生成 / 配表 / 资源 / 热更版本>
例外：<条款号 + 原因，无则填 无>
```

- **必须**一个 CL 对应一个可独立回滚的逻辑变更；**禁止**格式化、重构、功能修复混提。
- **必须**同时提交脚本 + `.meta` + 相关 Prefab / 场景 / 配置源表 / 生成产物，禁止拆成多个 CL 造成中间版本编译失败。
- **禁止**提交 `Library/`、`Temp/`、`Logs/`、`obj/`、IDE 用户配置、个人临时文件；忽略规则由工程统一维护。
- **禁止**提交二进制资源时未标注来源与导入设置变更。
- **推荐**活动/数值类高频改动单独 CL，便于灰度与回滚。

<a id="s-12-3"></a>

## 12.3 锁、冲突与 UI 协作

- **必须**对场景/Prefab/图集/配置源表按团队锁策略独占编辑，二进制及不宜语义合并的资产启用文件锁；`.asmdef` 为 JSON，`.asset` 等可能为 YAML，不能一概视为不可文本合并。可合并文件经人工复核并验证依赖/引用，策略由版本库配置明确。
- **必须**一个面板/弹窗一个明确 Owner，UI 改动提前在协作频道通告；**禁止**并行改同一 Prefab。
- **必须**冲突时先与对方确认语义再合并，禁止 `Accept Theirs` / 覆盖式强制解决。
- **必须**合并后重新生成 + 编译 + 面板回归，禁止"能编译就提交"。
- **推荐**大范围重构（改生成器、批量重命名、目录调整）选低峰期提交并提前通告。

<a id="s-12-4"></a>

## 12.4 提交前动作

1. `p4 sync` 到最新，确认无待解决冲突。
2. 手写代码变更执行编译、格式与静态分析（0 Error，无未获批准的新增 Warning）；涉及绑定/schema/源表/生成器时重跑对应生成链，确认源与产物一致；纯文档变更执行文档结构/引用检查。
3. 涉及 UI 时打开并关闭受影响面板/弹窗，检查断链引用、安全区、状态复位与弹窗队列；涉及资源导入/生命周期/SDK/性能时补目标平台验证。
4. 按 [§13](#s-13) 执行单测、回归、必要的配对测试与风险对应的真机验证，记录结果，不适用项须说明原因。
5. 用 `p4 opened` / diff 逐文件复核，**必须**确认无调试开关、临时日志、本机路径、渠道密钥夹带。
6. 涉及热更资源或配置时，**必须**在 CL 中记录版本号。

<a id="s-12-5"></a>

## 12.5 多渠道构建

- **必须**构建参数（包名、签名、渠道 ID、SDK 开关）由 CI 注入，禁止写入仓库或 Prefab。
- **必须**各渠道共用同一套资源、配置与代码；差异只允许存在于隔离的适配层配置。
- **推荐**提审包与灰度包的资源/配置版本可回溯到 CL 与 Label。

<a id="s-12-6"></a>

## 12.6 若项目改用 Git（选型替换映射）

| P4 条款 | Git 等价做法 |
| --- | --- |
| 独占锁 | Git LFS 文件锁 + `CODEOWNERS`，同一 Prefab 禁止并行改 |
| Changelist | 单个 PR / Commit，沿用 [§12.2](#s-12-2) 描述模板 |
| Stream / Label | 主干 + 发版分支 + Tag |
| `.p4ignore` | `.gitignore` + `.gitattributes`（二进制标记 LFS） |
| `p4 opened` / diff | `git status` / `git diff --cached` |

**说明**：选型由立项评审决定，本规范只约束"怎么做"，不锁定工具。切换工具时以上映射逐条落地，其余条款不变。

<a id="s-13"></a>

## 13. Code Review 与测试验证

<a id="s-13-1"></a>

## 13.1 Review 要求

- **必须**每个 CL 至少 1 名 Reviewer；涉及跨模块模式基础设施/架构框架选型、UI 框架、生成器、协议、配表 schema、发奖链路、性能热路径及更新系统的变更需模块 Owner 复核；选型记录按 [§2.8](architecture.md#s-2-8)，更新能力按 [§9.5](updates.md#s-9-5)。
- **必须**Review 覆盖适用项：职责/依赖方向、模式是否解决真实问题且成本适当、接口契约与可读性、复杂度与重复规则、状态校验、数据一致性/幂等、异步竞态、资源所有权、数值/时间边界、测试有效性，以及 UI/生成/性能/发布相关约束。
- **推荐**Reviewer 用 [§14](#s-14) 清单逐项打勾；涉及适配或打断的改动附真机录屏 / Profiler 证据。
- **禁止**以「能跑就行」「先合再改」放行含 [§0](../CODE_BASICS.md#s-0) 红线的改动。
- **必须**Review 结论区分阻断缺陷、需说明的风险和个人风格建议；已有格式/命名工具可检查的问题不反复人工争论。阻断项须解决并复核，超阈值例外须附原因、Owner 与补偿性测试/监测措施。

<a id="s-13-2"></a>

## 13.2 测试

- **本项目默认分层验证**：遵守[工程验证入口的范围选择](../../工程验证入口.md#默认按变更范围验证)。开发期快速复现/修复，稳定期仍以模块及直接依赖回归为主；普通提交不自动跑全量EditMode + PlayMode。只有新增风险/失败才扩大范围，阶段整体集成、广泛基础变更或发版按实际影响选择全量，任务中说明理由；已通过且输入未变不重复跑。
- **必须**新增/修改核心规则时提供 EditMode 单测（配置校验、状态迁移、发奖幂等、数值计算、远程覆盖回落）；面板栈、组件生命周期与场景交互使用 PlayMode 或等价自动化；SDK/IL2CPP/原生差异补目标平台测试。测试范围随风险变化，纯文档修改不强制跑全量真机。
- **必须**重构状态机或替换算法时保留行为基线并做同输入配对测试；新增功能按需求定义期望结果，修复缺陷须证明旧版本错误、新版本正确，禁止把旧缺陷当作必须保持的正确基线。
- **必须**覆盖受影响规则的正常/拒绝/异常路径，以及适用的空数据、上下界/溢出、重复调用、取消、超时、关闭后回调、乱序响应、断网恢复和读写失败；发奖/购买须验证重启补单仍不重发，不能只测按钮防抖。
- **必须**测试断言可观察结果及关键副作用（状态、余额、事件次数、持久化次数），而非仅“未抛异常”或照抄实现；测试彼此独立，时间/随机/网络可控，禁止用任意 `Sleep` 等待和反复重跑掩盖不稳定用例。
- **必须**使用 [§2.7](architecture.md#s-2-7) 中的模式时验证其适用契约：状态迁移与中断、事件重复/释放/重开快照、池对象复位与过期回调、策略一致的输入输出约束、创建失败清理，以及命令的重复/撤销/回放语义；未使用的模式不要求为清单另造实现和测试。
- **必须**涉及远程更新时按 [§9.7](updates.md#s-9-7) 验证兼容、打断、离线、坏版本拒绝及恢复；代码更新须从已发布兼容底包验证补丁，不能只测安装了全部最新内容的新整包。未采用代码热更时不要求补造热更链路。
- **必须**可自动化的缺陷修复补充“修复前失败、修复后通过”的回归用例；平台/人工条件限制无法自动化时，记录可复现步骤、原因与替代验证证据。
- **必须**UI/适配改动及发版回归执行竖屏真机矩阵：长屏（≥19.5:9）、刘海/挖孔屏、小屏（16:9 或 4:3）、中低端 Android 一台、iOS 一台；生命周期/SDK/网络改动补弱网/离线、切后台、广告打断与回前台。平台范围以立项支持清单为准。
- **必须**UI/本地化改动核对受影响页面的安全区和文本溢出；发版覆盖主界面、结算、商店、底部按钮栏与最长语言文案。

<a id="s-13-3"></a>

## 13.3 质量检查与 CI 门禁

**必须**执行基础质量检查；CI 用于自动阻断，不代表没有 CI 就可以免检。暂未自动化的检查由责任人提供可复核结果，并登记自动化落地计划。禁止声称“工具通过”却不记录执行命令/工具版本、结果与报告位置。

| 阶段 | 检查项 | 不通过时 |
| --- | --- | --- |
| 提交/合入：手写代码 | 目标配置编译、格式、静态分析、相关自动化测试、敏感信息扫描 | 编译错误/测试失败/未批准的新增诊断阻断；超复杂度触发线须重构或批准例外 |
| 合入：配置/绑定/资源 | 重生成与源/产物一致性、表校验、Prefab 断链/漏绑扫描、资源导入检查 | 非法配置、断链、产物不可复现阻断 |
| 合入：构建/SDK/平台 | 受影响平台或渠道的构建；发布宏与调试能力剔除验证 | 构建失败、生产包含可用安全旁路阻断；关键词扫描仅作辅助，不能替代构建验证 |
| 每日/定期构建 | PlayMode/机型冒烟、内存/帧率、包体增量、适配截图比对 | 超预算或回归失败必须排查，确认风险前不得进入发版候选 |
| 发版前 | 支持平台 IL2CPP/AOT 构建与真机、离线启动、存档迁移/恢复、广告/内购沙箱与补单、隐私合规、回滚预案；采用远程更新时补旧底包升级与失败恢复 | 关键链路失败或未验证阻断发版 |
| 纯文档 | Markdown 结构、章节引用、示例及变更记录检查 | 无效引用/错误示例修正后合入，不要求无关的全量客户端回归 |

<a id="s-13-4"></a>

## 13.4 静态分析、指标与基线

- **必须**将 `.editorconfig`、分析器/规则版本、严重级别、构建配置和忽略范围纳入版本控制；选用兼容当前 Unity 编译链的工具，不以个人 IDE 告警代替统一检查结果。
- **必须**把编译错误、程序集循环依赖、明确的安全/正确性错误与未处理资源泄漏作为阻断项；格式/命名可由工具修正。分析器发现的问题需结合语义复核，规则抑制按 [§4.14](csharp.md#s-4-14) 执行。
- **必须**对存量问题建带 Owner 的基线，新增/修改的手写代码不得无批准地增加同类问题；禁止反复刷新基线掩盖新增问题。生成代码、SDK 与第三方代码可排除风格/复杂度统计，但不能排除构建、安全和真实运行错误。
- **推荐**对新增/修改的纯业务规则，以行覆盖率 ≥ 80%、分支覆盖率 ≥ 70% 作为初始观察目标，落地时按工具能力与风险调整；核心资产/状态迁移的关键路径须逐项测试，不能用覆盖率均值抵消漏测。生成/第三方代码不计分母，禁止为达标写无有效断言的测试。
- **必须**联合看待测试结果、复杂度（[§4.9](csharp.md#s-4-9)）、重复规则、诊断增量和运行预算；任何单一数字达标都不等于代码正确。达成指标优先改善设计和测试，禁止只移动代码、改统计范围或降低门槛。

<a id="s-13-5"></a>

## 13.5 小团队落地顺序

| 优先级 | 最小落地内容 | 完成证据 |
| --- | --- | --- |
| 首批：立即执行 | 统一格式/编译规则、职责边界、基础单测、人工 Review、缺陷回归 | 仓库内规则文件、统一执行命令、首批测试与评审记录 |
| 次批：自动化阻断 | CI 编译/单测/分析器、生成一致性、配置/Prefab 校验 | 失败提交能被阻断；存量诊断有基线与 Owner |
| 持续：风险量化 | 覆盖率趋势、复杂度、真机性能/包体、补单与坏档恢复演练 | 可对比的报告、预算、回滚/恢复记录 |

**必须**在项目补充约定中为每项门禁写明负责人、适用范围、工具版本、执行命令、失败判定、报告位置与计划日期；分阶段的是自动化能力，不是正确性/数据安全底线。

## 14. 自检清单

<a id="s-14-1"></a>

## 14.1 提交前（开发者）

- [ ] 按变更范围完成编译/格式/静态分析，无未批准的新增诊断；涉及生成时源与产物一致
- [ ] 已遵守代码基础与项目基线，按任务范围核对适用专题
- [ ] 生成文件未被手改；源与产物同 CL、生成器版本已注明、无本机路径
- [ ] UI/业务/基础设施职责明确，依赖无环，核心规则可脱离场景测试
- [ ] 模式选择有真实场景，未为简单分支堆架构；跨模块基础设施/框架选型有轻量记录
- [ ] 已用模式的状态所有权、事件语义、池化复位/依赖生命周期等适用契约已验证
- [ ] 方法只做一个清晰动作，无复制规则/无意义抽象；复杂度超触发线有处理或批准例外
- [ ] 接口输入/结果/失败原因/副作用明确，前置校验完整，预期拒绝不滥打异常日志
- [ ] 数值单位、负值/上下界/溢出、时钟/时区与随机复现已检查
- [ ] 发奖/购买/存档有一致性与恢复方案，重复回调及重启补单不重复到账
- [ ] 事件 `+=/-=`、协程、定时器、对象池借还、弹窗注册成对
- [ ] 异步有所有者、取消/超时与异常观察，主线程/过期回调/乱序问题已处理
- [ ] 热路径分配预算已验证，默认稳态 0 B；无反复查找/无界缓存/无依据的全量扫描
- [ ] 序列化字段/枚举变更向后兼容，内部可变数据未泄露，无死代码及无主技术债
- [ ] 安全区、长屏/小屏/刘海、底部 Home 条已适配；无绝对坐标与整体缩放
- [ ] 弹窗队列、广告 / 内购 / 切后台打断与恢复已验证
- [ ] Inspector 引用无断链，Prefab 静态绑定完整
- [ ] 资源导入设置已确认（压缩 / Read/Write / Mipmap / 九宫格 / 音频）
- [ ] 配置校验通过；离线可玩，远程覆盖失败可回落；热更版本兼容已考虑
- [ ] 涉及更新时已区分配置/资源/代码，版本清单匹配底包与平台；旧包升级、失败恢复和存档兼容有证据
- [ ] 日志级别正确，无隐私/密钥/临时调试日志
- [ ] 相关单测/回归通过，配对测试/面板/生成链/真机验证按风险执行并有证据
- [ ] `.meta` 同进同出，锁已确认，CL 描述完整，渠道参数未入库

<a id="s-14-2"></a>

## 14.2 Review（Reviewer）

- [ ] 变更可独立回滚，未夹带格式化/无关改动
- [ ] 命名与实现行为一致，无隐式绕过校验
- [ ] 职责与依赖方向清晰，核心规则可测试，SDK 已被适配层隔离
- [ ] 不按模式数量评价设计；简单替代已考虑，新增框架/基础设施的收益与成本有依据
- [ ] 状态迁移只有明确入口，事件不承担隐式交易，单例不隐藏依赖，模式契约有测试
- [ ] 接口契约可理解，失败无未说明的部分写入，无复制规则/不必要抽象
- [ ] 复杂度/诊断/覆盖率按统一口径评估，未用刷新基线或无效测试规避门禁
