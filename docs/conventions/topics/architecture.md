## 2. 工程结构与程序集

<a id="s-2-1"></a>

## 2.1 目录约定

```
Assets/
├── Art/
│   ├── UI/Atlas/            # UI 图集，按面板/弹窗分
│   ├── UI/Frames/           # 九宫格底板、通用边框
│   └── Audio/               # BGM、SFX
├── Scenes/                  # Boot / Main（竖屏单主场景为主）
├── Prefabs/
│   ├── Panels/              # 全屏面板
│   ├── Popups/               # 弹窗：奖励、结算、广告、设置
│   └── Widgets/             # 复用控件：按钮、进度条、红点、商品卡
├── Scripts/
│   ├── Framework/           # UI 栈、事件、资源、网络、音频基础（无业务依赖）
│   ├── Generated/           # 共享配置/协议生成产物，禁止手写
│   ├── Config/              # 配置访问层、远程覆盖与版本兼容
│   ├── Network/             # 协议层、连接管理
│   ├── Modules/             # 业务模块；UI partial 生成文件随所属模块存放
│   └── Editor/              # 编辑器扩展，禁止被运行时程序集引用
├── Settings/                # URP、CanvasScaler、质量、输入配置资产
├── Plugins/                 # 广告/内购/埋点 SDK，保持原始目录结构
└── Resources/               # 原则上禁止新增，见 [§8.4](assets.md#s-8-4)
```

**必须**：`Scripts/Generated/` 内文件头部保留生成标记；生成器重跑后被覆盖属预期行为。
**必须**：业务代码不得反向引用 `Editor/` 程序集；编辑器工具不得影响运行时构建产物。
**禁止**：在 `Assets/` 根目录堆放脚本、临时场景、个人测试资源。
**推荐**：竖屏休闲项目以单主场景 + 面板栈为主，避免多场景切换带来的重复加载与状态丢失。

<a id="s-2-2"></a>

## 2.2 程序集定义（asmdef）

- **必须**按 `Framework` / 共享配置或协议生成层 / `Config` / `Network` / 业务模块 / `Editor` 等职责建立 asmdef，禁止全工程默认 `Assembly-CSharp` 大杂烩。UI 绑定生成的 `partial` 类型与其手写扩展必须在同一程序集/命名空间，禁止把所有生成文件机械隔离到独立 asmdef 导致类型无法合并。
- **必须**单向依赖：`Modules → Framework`，`Framework` 不得反向引用业务模块；跨模块通信走事件/接口。
- **必须**所有 Editor 脚本标记 `Include Platforms: Editor`，防止误打进运行时程序集。
- **必须**广告 / 内购 / 埋点 SDK 封装在独立适配层，业务模块禁止直接引用 SDK 类型（便于换渠道与打桩测试）。
- **推荐**按模块拆包缩短增量编译时间；新增 asmdef 需同步提交 `.asmdef` 与 `.meta`。

<a id="s-2-3"></a>

## 2.3 命名空间

```csharp
// 命名：项目.层.模块
namespace MyGame.Modules.Daily.UI
{
    public sealed class DailyRewardPopup : PopupBase { }
}
```

- **必须**与目录路径一致；一个文件一个主类型，文件名与主类型同名。
- **禁止**无业务语义的上帝类（`Utils` / `Common` / `Manager` 泛化命名需评审）。

<a id="s-2-4"></a>

## 2.4 生成代码边界

- `Scripts/Generated/`（或等价目录）下文件**必须**带 `// <auto-generated />` 标记。
- 生成源（UPF 面板描述 / Prefab 描述、Luban schema 与源表、生成模板配置）是唯一可修改对象。
- 生成结果不稳定时**必须**修生成器或模板，禁止在生成文件上打补丁后提交。
- 生成器版本升级**必须**全量重生成 + 编译 + 面板回归，禁止只生成单个文件。
- **禁止**生成产物中出现本机绝对路径、个人账号、本地时间戳；生成流程**必须**可由统一命令或 CI 复现，不依赖某台开发机。

<a id="s-2-5"></a>

## 2.5 职责划分、依赖与可测试性

- **必须**区分三类职责：UI/组件负责展示和输入；业务逻辑负责规则与状态迁移；基础设施负责存档、网络、资源和 SDK。禁止由按钮回调直接修改多份存档、调用 SDK 并完成发奖。
- **必须**让可独立计算的核心规则（奖励计算、解锁条件、状态迁移、配置校验）脱离场景与 `MonoBehaviour`，能够在 EditMode 中直接构造输入并验证输出。无需为了“纯净”而给每个简单类型增加接口。
- **必须**在启动/装配入口显式传入模块依赖；时间、随机数、存档、网络和 SDK 等非确定性边界须可替换，以便测试。禁止业务逻辑通过全局查找、任意单例链或 Service Locator 隐式取得依赖。
- **必须**保持程序集依赖图无环；数据生成与 UI 绑定生成依赖不同时应拆分程序集，禁止为消除编译错误反向引用业务层。跨模块调用须有明确契约，禁止读取另一模块的内部可变字段。
- **必须**区分命令与通知：需要结果、顺序或错误处理的操作使用显式方法/接口；已发生事实的广播可用事件。禁止把完整业务流程藏在无顺序保证的全局事件链中。
- **推荐**优先组合而非深继承，沿用工程已有服务与扩展点；只有真实重复、稳定边界或外部依赖替换需求出现时再抽象。禁止为尚未出现的需求引入通用框架、万能管理器或多层空转发。

<a id="s-2-6"></a>

## 2.6 游戏设计模式与架构选型

**约束的是问题、边界和行为，不是模式数量。** 项目必须满足职责清晰、状态受控、依赖可见和可测试等质量要求；实现可采用普通方法、枚举或组合对象，不要求每个模块都套模式。下表的“默认建议”不新增一套强制技术栈；现有框架已提供的能力优先复用，涉及 SDK 隔离、列表复用等已有强制要求仍按对应章节执行。

| 模式/方案 | 适用的游戏场景 | 默认建议与使用边界 |
| --- | --- | --- |
| 状态模式 / 有限状态机（FSM） | 局内开始/进行/暂停/结算、广告流程、角色行为 | **推荐**对互斥状态和明确迁移建模；简单枚举 + 显式分支即可，只有状态行为复杂时才拆状态类；禁止每个开关都建一套 FSM |
| 观察者 / 类型化事件 | 余额变化刷新多处 UI、任务进度通知、结算后的音效/展示 | **推荐**广播已发生的事实；需要返回值/确定顺序的主流程走显式调用，禁止用全局事件总线串扣费/发奖 |
| 对象池 | 列表 Cell、频繁生成的特效/飘字、实测高频分配对象 | **推荐**按分配和生命周期需求使用；列表复用按 [§6.1](ui.md#s-6-1) / [§6.4](ui.md#s-6-4) 执行，其他低频对象不强制池化，禁止为池化常驻大量闲置资源 |
| 策略模式 | 确有多种且独立变化的计分、掉落、目标判定算法 | **可**通过同一契约替换算法；只是数值不同优先配表，简单固定分支保留清晰的 `switch`，禁止每个配置 ID 对应一个空策略类 |
| 工厂 / 创建入口 | 实体/控件有多种创建方式、需要注入依赖或统一接入资源系统 | **可**集中创建、初始化和失败清理；UI 必须来自合法 Prefab/绑定，工厂不能绕过资源层或自行拼装界面树 |
| 适配器 / 门面 | 广告、内购、存档、平台能力与外部 SDK | **必须**保持外部类型与业务隔离；门面只暴露业务需要的能力，禁止演变为包办所有模块的总管理器，见 [§2.2](#s-2-2) |
| 命令模式 | 真实存在的操作排队、录像重放、关卡编辑器撤销 | **按需**引入；普通按钮调用不必包装成命令，购买/已到账奖励不是可随意撤销的编辑操作 |
| 单例 | 确需应用级唯一的服务实例 | **限制使用**，不作为业务访问默认方式；“只创建一个实例”不等于“所有代码都能 `.Instance` 随意访问”，具体约定见 [§2.7](#s-2-7) |
| 依赖注入（DI） | 时间/随机/存储/SDK 替换、模块装配与测试 | **推荐**显式传入依赖；普通 C# 类型优先构造注入，Unity 组件可用 Inspector 或显式初始化，不强制引入 DI 容器 |
| MVP / MVVM 等 UI 分层 | 状态复杂、需要隔离展示和业务规则的面板 | **推荐**按 [§2.5](#s-2-5) 分责，复用已有 UI 框架；简单面板不强制凑齐 Model/View/Presenter/ViewModel 多层，禁止两套状态源互相同步 |
| 组件组合 / ScriptableObject 配置 | 实体能力复用、可编辑且可共享的静态定义 | **推荐**组合有明确职责的组件，配置只读；禁止组件相互循环查找，或将共享资产直接作为每个实体的可变运行态 |
| 行为树 / ECS-DOTS / 自研通用框架 | 复杂 AI 决策或经测量的大规模实体/性能问题 | **需评审**实际规模、调试工具、平台与团队成本；本项目基线不因“游戏开发通常这样”默认采用，也不为假设的规模提前重写架构 |

**说明**：FSM、观察者等是行为组织方式，MVP/MVVM、ECS 等属于架构方案，DI 是依赖管理方式，`ScriptableObject` 是 Unity 资产机制；这些不是同一层面的可替换选项，不能拿术语数量评价代码质量。未列出的模式并非禁止，按 [§2.5](#s-2-5) 的职责原则及 [§2.8](#s-2-8) 适用的选型要求评估即可。

<a id="s-2-7"></a>

## 2.7 常用模式的落地约定与反模式

- **状态机**：必须指定状态所有者和唯一迁移入口，明确合法迁移、失败/中断/恢复行为；一次实际迁移的退出/进入动作只执行一次。禁止外部直接改状态字段、在多个组件维护同一状态，或在进入回调中无限嵌套切换。异步状态退出后旧结果不得推动新一轮会话；动画状态可驱动表现，但不能代替业务状态或充当唯一发奖凭证。
- **事件通知**：必须明确事件拥有者、有效范围和派发线程，使用强类型载荷，按 [§4.15](lifecycle-async.md#s-4-15) 管理订阅。完成类事件在对应状态/数据提交成功后发送，失败或待确认状态不能冒充成功；监听者异常按统一策略报告，不能把已完成交易改报为未执行。面板重开须读取当前快照，不能依赖“曾经收到过事件”，也不能靠监听顺序保证正确性。
- **对象池**：优先使用工程已有实现或适用的 `UnityEngine.Pool`，统一租借/归还接口；区分最大闲置容量与活跃数量峰值，定义超额创建/降级策略。归还须停止动画、取消展示任务、清除订阅/绑定并复位；按 [§4.7](lifecycle-async.md#s-4-7) / [§4.15](lifecycle-async.md#s-4-15) 隔离旧回调，禁止把“不销毁对象”等同于“无需清理”。
- **策略与工厂**：策略只处理所属规则，不越权保存、扣费或直接操控 UI；先确认变化的是算法还是参数。工厂/资源入口明确调用方与对象所有权，创建失败须清理半成品；禁止使用反射扫描/字符串类名在热路径任意实例化，也禁止从远程配置执行任意类型。
- **单例与依赖装配**：允许在启动装配入口持有应用级唯一服务，但业务通过显式依赖使用；遵守 [§2.5](#s-2-5)，禁止层层 `.Instance` 链和隐藏创建。单例服务必须明确初始化、销毁和测试复位策略，覆盖禁用 Domain Reload 时的重复订阅/残留静态状态；不能用 `DontDestroyOnLoad` 掩盖错误生命周期。
- **UI 分层与组件组合**：UI 接收输入并展示状态，规则与资产由所属业务服务修改；Presenter/ViewModel 是展示适配层，不是另一套玩家资产库。配置资产与运行态分离，实体专属状态应独立创建；如需克隆 `ScriptableObject`，须确认嵌套引用是否仍共享，不能假设浅层复制即完全隔离。
- **命令、撤销与回放**：引入时须定义命令数据、顺序、失败/重复执行、版本兼容及历史容量。可撤销命令明确逆操作，网络写入/支付走事务与补偿而非本地 `Undo()`；可回放须控制输入、随机种子、时钟及模拟版本，不能仅记录按钮点击就宣称确定性，Unity 物理默认不保证跨平台确定性。

## 2.8 典型流程与选型记录

**例：一次关卡结算，不必叠加所有模式。** 以下仅描述职责与数据流，类名和框架按项目实际实现：

```text
结算输入
  -> 会话服务校验状态，沿用本局结算 ID，进入“结算中”
  -> 奖励规则计算结果（仅在确有算法变化时使用策略）
  -> 按权威归属确认并提交奖励/结算状态，失败按恢复记录处理
  -> 提交成功后发布结算完成事实
  -> 展示层读取结果/当前快照，刷新结算面板
```

- **推荐**用明确的会话状态和显式服务调用控制主流程，事件只通知后续展示；工厂/对象池仅在需要创建或复用展示对象时介入。模式可以组合，不要求为此流程另造状态机框架、命令总线和 DI 容器。
- **必须**给适用的边界留验证：重复输入不重复结算，提交前失败不半发奖，超时结果未知走确认/补单，提交后展示失败可重开恢复；关闭面板不取消已提交交易，见 [§10.3](data-security.md#s-10-3)。此流程的正确性不能依赖某个 UI 监听者成功运行。
- **必须**首次引入跨模块模式基础设施、第三方架构框架，或替换既有架构时做轻量选型记录并由模块 Owner 复核；局部复用现有模式无需重复写长文档，提交说明足够。禁止只写“采用某模式，所以更解耦”而不说明实际收益。

选型记录至少回答：

| 项 | 要回答的问题 |
| --- | --- |
| 当前问题 | 哪个真实需求、重复规则或实测瓶颈需要解决？ |
| 简单替代 | 普通方法/枚举/配置/现有框架为什么不足？能否少一层？ |
| 选定边界 | 谁持有状态、创建实例、发起迁移、释放资源？哪些调用必须有顺序？ |
| 成本与迁移 | 增加哪些依赖/调试成本，是否影响序列化、AOT、性能和已有模块？如何分步迁移？ |
| 验证方式 | 正常、失败、打断、重入怎样测试？性能收益是否有数据，撤回方案是什么？ |
