## 9.5 更新能力分级与框架选型

**本项目默认建议**：先统一配置访问与资源加载入口，按运营需求启用远程配置/资源更新；不默认引入 C# 代码热更新。若已确认长期运营且必须在整包发版间隔内修复或迭代逻辑，应在首个正式底包前完成代码热更的最小验证，不能假设上线后仅靠下发一个 DLL 就能补上运行时能力。

| 需要改变什么 | 能力与候选方案 | 边界 / 判断 |
| --- | --- | --- |
| 奖励数值、活动时间、关卡参数、功能开关 | Luban 随包表 + 兼容的远程覆盖 | 优先配置更新；只能调用已存在且允许的能力，不能新增任意 C# 行为，也不能用开关替代安全校验 |
| 图片、音频、现有逻辑支持的关卡/Prefab | 现有资源管理器的远程内容更新；Addressables 或 YooAsset 等按团队选一种 | 资源更新不提供新脚本实现；Prefab 的组件类型、序列化格式与依赖必须被客户端支持；跨平台资源分别构建 |
| C# 业务逻辑、现有玩法缺陷修复 | 确需代码更新且平台允许时，C# 团队可优先验证 HybridCLR | 增加运行时/构建链、AOT/泛型/裁剪兼容、补丁发布与回归成本，不能按“接个包就好了”估算 |
| 已有成熟 Lua 团队/工程的脚本逻辑 | 可评估 xLua 等既有脚本方案 | 复用已有经验；无 Lua 基础的小团队不因热更单独引入双语言体系，更不默认同时采用两套代码热更方案 |
| Unity 引擎、原生 SDK、权限/签名/原生插件或不兼容底层接口 | 整包更新，按渠道要求发布 | 托管脚本框架不能替换所有原生能力；不能承诺靠热更新修复任意 SDK/引擎问题 |

**引入代码热更前必须确认**：有不能由配置/资源或合理整包发版满足的实际逻辑更新需求；目标平台/渠道允许该更新方式与具体内容；团队有人维护构建发布/监控/恢复链路；目标设备上的性能、包体与内存成本可接受。以上未确认时先保留清晰边界和整包更新方案，不为未来可能性构建完整热更平台。

- **必须**把“技术可运行”与“渠道允许发布”分开评估。Apple App Review Guidelines 2.5.2 对下载/执行会引入或改变功能的代码有明确限制；框架宣称支持 iOS 不能作为通过审核的依据。各 Android 渠道、小游戏/Web 平台也须依据具体容器与规则确认，不能直接沿用原生应用结论；禁止将热更用于绕过审核。
- **必须**按 [§2.8](architecture.md#s-2-8) 记录选型、适用平台/内容范围、Owner、版本/许可、发布成本与禁用/整包兜底方式；锁定 Unity 补丁版本、框架版本、构建环境与资源方案的兼容组合，禁止只写“Unity 2022.3 通用支持”。已有资源系统可满足需求时优先复用，不强制更换。
- **推荐**用最小闭环验证再选定：从旧正式配置的 IL2CPP 底包下载新业务补丁与匹配资源，执行泛型/异步/序列化/UI 绑定路径，再验证离线启动、下载中断、错误补丁拒绝和恢复。编辑器里 `Assembly.Load` 成功不能代替真机验证。

参考资料（2026-11-13 核对；实施与发版时重新确认目标版本和平台规则）：[HybridCLR 官方介绍](https://www.hybridclr.cn/docs/intro)、[Unity Addressables 内容更新工作流](https://docs.unity3d.com/Packages/com.unity.addressables@1.21/manual/ContentUpdateWorkflow.html)、[YooAsset 官方仓库](https://github.com/tuyoogame/YooAsset)、[xLua 官方仓库](https://github.com/Tencent/xLua)、[Apple App Review Guidelines 2.5.2](https://developer.apple.com/app-store/review/guidelines/#software-requirements)。文档列出候选不代表已锁定选型，也不保证当前最新版与项目兼容。

## 9.6 代码热更的程序集、AOT 与运行边界

本节仅适用于已批准使用代码热更新的工程；不采用时保留原有模块结构，无需凭空增加 HotUpdate 层。

- **必须**明确随底包发布的启动/更新/恢复层、稳定契约与可更新业务层。AOT 侧通过接口/注册等约定接入热更实现，禁止静态引用只能在补丁中提供的类型或形成程序集循环；边界使用兼容的数据契约，不以程序集名字“看起来分开”代替依赖检查。
- **必须**按实际框架/版本处理 AOT 泛型、补充元数据、方法桥接与代码裁剪所需产物；与目标底包/平台绑定生成并归档，禁止从任意历史包复制。`link.xml` / Preserve / 反射与生成绑定的类型保留须经 IL2CPP 真机测试确认，不能假设解释执行就无 AOT 限制。
- **必须**让同一类型的 UI 生成 `partial` 与手写部分位于同一程序集及同一更新侧，见 [§2.2](architecture.md#s-2-2)；配置生成类、跨边界 DTO 与 Unity 序列化类型按兼容策略放置。新资源若依赖新脚本/字段，必须与代码一起构成可校验的完整版本，禁止先发布资源让旧客户端加载未知组件。
- **必须**热更入口支持“一次启动、一次初始化”，管理静态状态、事件与资源所有者；默认在重启应用后的安全启动阶段切换版本。除非选定版本已验证卸载/热重载能力，不得假设可在运行中卸载旧程序集、替换所有存活对象并无损继续。
- **必须**把逻辑热更限制在已验证边界内；引擎/原生 SDK/平台权限/签名与不兼容的基础契约变更走整包。崩溃发生在补丁启动之前时，须由底包恢复路径或整包修复处理，不能指望尚未执行的补丁自救。

## 9.7 更新发布、离线与恢复验证

- **必须**发布清单绑定底包 Build ID/兼容范围、平台/架构/渠道、代码/资源/配置版本与存档 schema 兼容范围，携带文件大小、完整性信息及可信签名/验证元数据。客户端先检查兼容与可信来源，再下载到暂存区、完整校验、在安全点切换；禁止分别覆盖正在使用的 DLL、Catalog 或配置造成版本混搭。
- **必须**归档每个已发底包对应的构建输入、资源内容状态/清单及框架要求的 AOT 产物，按其兼容规则生成内容更新；不可复用时明确整包更新，禁止用最新工程随意生成文件覆盖全部历史版本。CDN 内容使用不可变版本路径，发布顺序保证文件先就绪、清单后生效。
- **必须**保留可工作的随包基线及适用的最近有效版本，首次启动和离线时核心内容按既定范围可玩；可选更新失败不阻塞主界面，新内容未下载时明确不可用状态。若安全/协议问题确需强制整包升级，应显式说明受影响范围、升级引导及离线基线例外，不能伪装成无限下载/重试。
- **必须**支持按底包/渠道/人群灰度、暂停发布与兼容范围内恢复，监控校验失败、启动异常、下载耗时和核心链路结果；本地记录版本切换与健康状态，避免坏补丁反复启动。恢复入口须在底包中可达，不能依赖已损坏的热更业务 UI。
- **必须**区别回退文件与回退数据：新代码可能已迁移存档/提交交易，旧补丁未必还能读取。先验证前后版本的数据兼容；不兼容时采用向前修复或受控恢复，禁止自动覆盖好档或把代码回滚等同于撤销支付。版本防降级与受控回退须由可信发布序号/清单授权协调，禁止为了回退关闭校验。
- **必须**在所有支持的底包兼容分组及目标平台验证：正常更新、跨版本/已知最低支持版本更新、离线首次启动、弱网/取消、空间不足、下载中断/进程被杀、文件缺失/损坏、签名不符、版本不兼容、启动失败与恢复；代码/资源混搭要被拒绝，补丁更新后补单仍须幂等。任何无法恢复的关键失败阻断发布。
