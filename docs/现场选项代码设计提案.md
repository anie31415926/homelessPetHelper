# 现场选项代码设计提案

日期：2026-11-18。状态：用户询问“选项功能代码准备怎么设计”；本文为结合当前源码的技术提案，**不是开工记录**。文案风格已确认，不等于[方法效果](现场救助选项候选清单.md)或[重复与趣味机制](重复行动与趣味选项设计.md)全部已确认。以下新增类型名仅用于说明职责，不先建空框架。

**最新实现**：用户随后确认轻量 JSON 并授权开工，首版元数据/文案分离、受限趣味供给、静音回复/拍照与稳定短反馈已接入既有 Editor 案例，见[当前实现与验证](选项管理模块实现记录.md#2026-11-18-json-与提示型趣味项)。下文完整架构仍是分步目标，不把多目标绑定、连续剧情、完整事实列表、正式距离或存档写成已完成；正式 Player 的配置引用/加载尚未接入。

**后续确认与范围收敛**：用户认可技术方向与最小版三条规则：趣味项消耗本回合选择、动物按当前条件正常回应；每手至多一项且计入锁定，保留真实稳定选择；首版聚焦静音回复/拍照。用户进一步明确“趣味项后续有空间再做额外效果，目前可以就选完后弹个提示文案”。因此首版不要求手机演出、连续剧情或专属动物增益/惩罚；提示不能虚构动物状态已改变，也不自动把该项等同一次加速恢复的等候。本轮继续回答数据存储问题，未开始改功能代码；下文完整目标分步落地，以此收敛范围优先。

## 1. 复用什么，补什么

| 当前事实 | 设计取向 |
| --- | --- |
| `Modules/Rescue/Options/RescueOptionHand` 已负责实例身份、锁定、消耗、换轮和会话/阶段校验，不负责抽取与动物规则 | 保留这个容器，不重建选项系统，也不让它持有情绪、手机消息或动画 |
| `RescueActionDefinition` 目前只有 ID，`RescueOption` 包含实例 ID、定义与锁定状态 | 容器继续只识别行动身份；内容元数据与目标绑定由外层管理，不把所有内容塞进底层定义 |
| Editor 的 `RescueCaseTrial` 组织五种样例方法，`GetActionFailure` 供发牌与执行使用 | 以此为迁移起点，抽出同一套可测试评估/结算，不新增另一条平行试玩流程 |
| `CaseAnimal` 使用 `HasSpace`、`IsWithinReach` 等样例开关，`Respond` 每次返回一个 `CaseResponse` | 不能仅加枚举就宣称支持多次位移和复合回应；正式位置表达待玩法确认，结果需要能表达多个已发生事实 |
| `AnimalIndividual` 已是个体状态唯一可变归属，现场与站内共享同一个体 | 不新建第二份饥饿、情绪或健康状态；场景物件、玩家位置和手机插曲不塞进动物档案 |
| `RescueCasePresenter` 读取 JSON 文案，并按现场情况切换退开标题；静态白板 Prefab 已存在 | 沿用展示与绑定结构，新增内容不重建 Prefab；将散落的标题/反馈选取逐步集中为展示映射 |

## 2. 行动、牌面与本次对象分开

建议在既有 Rescue 业务模块内用普通只读 C# 定义组织一个小型行动目录，不先引入 Luban、脚本语言、行为树或节点编辑器：

- **行动 ID**决定做什么，例如 `give-space`、`phone.reply`、`phone.photo`；不靠中文标题判断行为。
- **供给分组**用于实际方法/插曲族去重；“退开”和幽默包装不会成为两种能同时占位的方法。具体插曲分组由选定内容决定，不把所有手机行为一刀切成相同作用。
- **表现键**指向标题、提示、反馈及表现映射；改文案不改变行动效果。文字内容继续与规则分开，初期沿用本地文案表，配置生成器尚未定案。
- **本次绑定**记录实际干扰目标、消息 ID 或插曲步骤等，仅在行动需要时有值。由会话按选项实例 ID 持有，锁定后保留同一对象与含义；消息失效不偷偷改成回复另一条消息。

牌面选定后稳定展示；反复刷新 UI、开手册或锁定不重新抽标题、不推进随机源。若仍适用但前提变化，只更新可用原因/提示；失效保留项沿用已确认规则。

## 3. 规则评估与供给

用一处无副作用评估（暂称 `ActionEvaluation`）区分以下问题，而不是只返回“现在能否成功”：

| 问题 | 示例 |
| --- | --- |
| 本次还值得出现吗？ | 已经投喂足量且无其他用途就不新发；有新消息才有回复后续 |
| 有准备价值吗？ | 暂缺接近机会但以后可能用到，可提前保留 |
| 此刻能否执行，原因是什么？ | 物资不足、原消息已结束、安全禁忌、选项过期不能执行；“不能推进”不一律等于“不可执行” |
| 对最新局面是否真能稳住？ | 按动物意图、现场与目标评估，不在配置里写一个永久安全标记 |

供给、不可用提示和提交校验复用同一规则；提交仍必须用最新快照重评，不能相信 UI 几秒前的判断。普通可解释的错误尝试与非法输入分开：前者可消耗行动并产生已确认的动物回应，后者拒绝且无副作用。

外层供给器（暂称 `RescueOptionSupply`）依次处理保留项、过滤、方法分组去重、当前稳定选择与内容抽取，再将完整结果交给现有 `TryRefresh`。安全分类必须针对本次绑定，失效的保留项不能被算作安全兜底。抽取使用会话可控种子，规则回应不额外摇成功概率。

“一手至多一项趣味插曲”已获首版认可，包含锁定项，可以完全不出现，不能挤掉真实稳定选择。数量不足或锁定组合无合理供给，应在内容验证中明确报缺口，提交失败不留下半副牌；不静默解锁、凑同义牌、减少位置或新增临时规则。本方案本身不证明全部状态已覆盖。

## 4. 重复历史与插曲状态

由现场会话持有紧凑的 `ActionHistory` 与插曲进度：最近行动/分组、连续有效使用情况、已使用的少量文案键，以及当前消息或拍摄插曲的明确步骤。历史在成功提交后更新，拒绝、预览、锁定和重播不计次，不建立无界全文日志。

重复规则读取“当前事实 + 相关历史”，而非统一递减收益：

- 再退一次要从最新位置产生真实位移；若无用途则不新发，不靠重复次数假装移动。位置字段/距离值的正式设计仍待确认。
- 再次交流/玩耍依当前意愿与关注；不能只因连续次数到三就让它生气，也不能在每次换轮抹去兴趣变化。
- 回消息使用小型枚举步骤或明确分支即可，例如“尚未回复 -> 已回复 -> 有实际后续 -> 结束”；下一段何时出现仍按批准后的内容规则，不承诺必抽下一段。
- 不同文案只是同一行为的变体；需要新后果时必须有新的对象、条件或情节，不用改标题绕过去重。

现场物件与插曲留在现场会话；个体真正发生的经历由同一 `AnimalIndividual` 承接。跨相遇记忆与存档范围另行设计，不把回复微信记录自动变成动物永久记忆。

## 5. 一次提交与复合结果

由现场会话统一处理输入，保持现有会话/回合/选项实例校验，核心逻辑不依赖 `MonoBehaviour`：

```text
提交本轮选项实例
  -> 核对会话、阶段、暂停、实例及本次绑定
  -> 以最新状态重评前提，预构造行动、动物回应和成本的完整结果
  -> 再核对状态版本，在同一业务提交中消耗选项、提交状态、记录历史
  -> 返回不可变的 TurnResult
  -> 展示已发生的动作与回应
  -> 本轮回应展示结束/跳过后，才允许下一轮选择；满足收尾条件则走独立入口
```

不能先扣牌/扣食物，再发现动物快照已变而普通拒绝。实际实现需让规则所有者在同一调用线程、无中途外部回调的边界内完成预校验与提交；若容器需要补只读校验/准备入口，复用它的原校验逻辑，不在外层复制一份。与 `AnimalIndividual` 的最新快照校验共同覆盖，不把多个仍可拒绝的 `Try` 随意串联就宣称原子完成。

`TurnResult` 建议包含本轮身份、提交前后必要快照、成本/耗时依据、按因果排序的结构化事实与反馈键。例如一次静音回复可同时表达“消息已回复”“动物继续取食”“食物已被吃掉”；不再只能从“回消息”与“吃东西”两个单一结果里二选一。游戏时间由所属时钟入口按同一结算身份提交一次，当前试做尚无这项接入，不借此确定分钟数或双计动物活动耗时。

事实列表是方法返回的数据，不是通用事件总线。先执行玩家动作，再以更新条件评估动物自主回应，记录实际发生的结果；不会只有选等候才让动物行动，也不会无条件执行一整套全部状态转换。

## 6. 文案与画面只解释结果

展示映射读取本轮结果与相关历史，输出已经确认的自然、克制文案，以及动作主体、顺序和场景变化；UI 不自行加信任、扣物资或推进插曲。

- 同一结果可以先演玩家看手机，再演动物继续吃；实际后退与动物移动要分开，不能仅缩放动物图冒充位移。
- “还是背影”“主角出画了”必须有实际对应事实。如果当前玩法尚未表达朝向或取景范围，就用中性反馈，不能为了笑话先捏造这些结果或暗定镜头方案。
- 一次回应的文案变体选定后按结果身份保留；重绘、暂停恢复、重播不能重抽包袱或重新执行行动。只改变文字的变化不进入业务随机流。
- 动画/文字播完只解除下一次输入的展示等待，不重新计算成功。重复完成回调、旧会话回调、面板关闭重开不重复扣牌或推进；当前先验证活会话内恢复，不承诺尚未实现的磁盘存档。

## 7. 建议的落地顺序与验证

1. 保留既有两个试玩起点、同一个体和选项容器；把评估、供给与复合结果边界从当前案例分清。通用规则放 `Modules/Rescue`，Editor 只留入口、样例配置与试做装配，不把整个含站内演出的 Trial 直接搬成正式引擎。
2. 按用户最新简化先接静音回复/拍照的提示型趣味选项，正常消耗选择、显示短反馈，不附加专属状态效果；动物的普通回合回应与趣味提示分开，不把一句玩笑当规则结果。连续剧情、拍摄表现和额外效果留待后续，不一次实现候选表全部内容，不重做白板或图片。
3. 再逐项扩充确认过的方法与重复分支；只有数量/独立差异真的需要时才拆少量专用处理器，不为每张牌造一个空子类，不做万能效果脚本。

关键测试：拒绝后牌/物资/个体/历史均不变；同样条件历史与行动得到同样结果；连续动作有真实差异或明确无用途；失效锁定对象不换义；锁定组合去重与安全兜底；插曲不替代接受安置；动画重复/暂停恢复不重复结算；改标题不影响行为。供给候选不足要有明确验证失败，不能靠自动化通关证明内容完整。

## 8. 数据与文案存储建议

### 静态内容用两份本地 JSON

工程已有 `Assets/EditorScenes/RescueCaseText.json` 和 `OptionPreviewText` 的 `entries / key / value` 读取及重复键校验。建议沿用这种轻量格式，新增可共用内容放在非 Editor 专用的普通资产目录（建议 `Assets/Settings/Rescue/`），文件名暂定：

| 文件 | 只保存什么 |
| --- | --- |
| `RescueOptions.json` | 行动 ID、实际分组、类别、标题键和反馈键等只读选项元数据，不直接写中文台词或动物运行状态 |
| `RescueOptionText.zh-CN.json` | 标题、提示、反馈的键值条目；中文集中维护，将来多语言新增对应文案文件，不复制规则 |

首版已落地的元数据行示例：

```json
{
  "id": "phone.reply",
  "groupId": "phone-message",
  "kind": "Flavor",
  "titleKey": "option.phone.reply.title",
  "feedbackKey": "option.phone.reply.feedback"
}
```

```json
{
  "entries": [
    { "key": "option.phone.reply.title", "value": "女友来消息了，先回一下" },
    { "key": "option.phone.reply.feedback", "value": "回完消息，收起手机。" }
  ]
}
```

首版可先固定一条反馈，不为提示功能建立多段插曲状态。反馈只声称确定发生的动作；是否继续吃饭由实际动物回应决定，不固定写进回消息文本。后续需要重复变体时，增加明确的文案键引用或结构化条件，不用标题来分派行为。

### 读取与修改入口

- 两份 JSON 作为 Unity `TextAsset` 随包，通过明确资产引用传给装配入口，初始化时解析为类型明确的只读目录；选择时不反复读文件。不新增 `Resources.Load`、绝对磁盘路径、远程配置或真实社交平台接口。
- 复用当前 JSON 格式与校验经验，不让运行时程序集依赖现有 Editor-only 的 `OptionPreviewText`。试做入口可先使用 Editor 装配，真正共用的解析/内容访问能力放在合适的运行时边界，避免复制规则与文本来源。
- 校验重复 ID、未知类别、缺失文案引用和格式参数；配置有错在开发验证中明确失败，不静默显示缺失键，也不边读边生成一副不完整手牌。
- 第一版 JSON 本身是唯一手工维护源。不再把同一新文案存回旧案例文本或硬编码在按钮里；旧案例文件继续保留其余现有内容，拆分时明确各条目的唯一来源。
- 当前不需要数据库或大型配表框架。内容增加、确有多人表格编辑需要时，再选择表格源与统一导出流程；届时从源表生成 JSON，不同时手改两边。格式版本可做轻量标识，不据此实现热更新。

### 运行进度与静态配置分开

选项实例、锁定、当前回合、近期使用与已选反馈归会话内存，个体状态仍由 `AnimalIndividual` 持有；不修改原 JSON 或共享配置资产。当前不补磁盘存档；将来做存档时只保存稳定 ID、必要进度及版本，不把整份文案表或 Unity 对象写进 `PlayerPrefs`。因此改文案不要求改玩法代码或旧存档中的中文内容。

本提案最初整理轮只核对源码与记录设计；后续 JSON 首版已获授权并实现，实际文件、试做参数及验证以页首链接为准。首轮 3/1/2 不变，具体距离、阈值、耗时、正式插曲频率和未确认后果仍不先写死。
